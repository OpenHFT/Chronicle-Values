= Project Requirements: Chronicle Values
:toc:
:lang: en-GB
:sectnums:
:source-highlighter: rouge

This document outlines the requirements for utilizing Chronicle Values.
The requirements are tagged using the company-wide Nine-Box taxonomy with the project scope `CV` (Chronicle Values).

See `AGENTS.md` for the global policy on tag usage.
The Nine-Box scheme covers `FN` for functional behaviour, `NF-P`, `NF-S` and `NF-O` for performance, security and operability, `TEST` and `DOC` for testing and documentation, `OPS` for operational concerns, `UX` for user experience and `RISK` for compliance.

See link:decision-log.adoc[Decision Log: Chronicle Libraries Usage] and link:../docs/decision-log.adoc[Chronicle Values - Decision Log] for related architectural decisions.

== Functional Requirements (FN)

* *CV-FN-001:* The system *must* support representation and manipulation of highly structured data with a fixed, compile-time known schema.
** _Source:_ Chronicle Values is designed for this.
* *CV-FN-002:* The system *must* support handling of unstructured, raw binary data, or data with dynamically determined/evolving schemas.
** _Source:_ Chronicle Bytes is designed for this.
* *CV-FN-003:* The system *must* provide mechanisms for defining and accessing complex, nested data structures.
** _Source:_ Chronicle Values supports nested value interfaces; Chronicle Bytes allows manual representation.
* *CV-FN-004:* The system *must* support efficient inter-process communication (IPC) for structured data.
** _Source:_ Chronicle Values flyweights on shared memory.
* *CV-FN-005:* The system *must* support efficient IPC for raw byte streams.
** _Source:_ Chronicle Bytes on shared memory/memory-mapped files.
* *CV-FN-006:* The system *must* provide mechanisms for efficient serialization and deserialization of Java objects to/from byte representations.
** _Source:_ Chronicle Bytes (BytesMarshallable) and Chronicle Values (generated BytesMarshallable).
* *CV-FN-007:* The system *must* allow for data definition using Java interfaces for structured data types.
** _Source:_ Chronicle Values core concept.
* *CV-FN-008:* The system *must* support interaction with Chronicle Map and Chronicle Queue using efficiently represented keys and values.
** _Source:_ Chronicle Values for fixed-size keys/values; BytesMarshallable for others.

== Non-Functional Requirements - Performance (NF-P)

* *CV-NFP-009:* The system *must* target ultra-low latency for data access and manipulation operations.
** _Source:_ Core design goal of both Chronicle Bytes and Values.
* *CV-NFP-010:* The system *must* support high throughput for data processing.
** _Source:_ Core design goal of both Chronicle Bytes and Values.
* *CV-NFP-011:* The system *must* minimize Garbage Collection (GC) impact by extensive use of off-heap memory for data storage.
** _Source:_ Key feature of Chronicle Bytes and Chronicle Values flyweights.
* *CV-NFP-012:* The system *must* provide "zero-deserialization" access for structured data where appropriate, avoiding hydration into heap objects for reads.
** _Source:_ Chronicle Values flyweights.
* *CV-NFP-013:* The system *must* ensure predictable performance characteristics, particularly for data access patterns.
** _Source:_ Fixed-layout nature of Chronicle Values; controlled access in Bytes.
* *CV-NFP-014:* The system *must* support atomic operations for concurrent, lock-free programming paradigms.
** _Source:_ Chronicle Bytes (e.g., compareAndSwapInt) and Chronicle Values (generated atomic methods).
* *CV-NFP-015:* The system *must* allow for efficient memory alignment of data fields to optimize access, especially for atomic operations and cache performance.
** _Source:_ Chronicle Values (@Align annotation); manual management in Chronicle Bytes.

== Non-Functional Requirements - Operability (NF-O)

* *CV-NFO-016:* The system *must* support deterministic release of off-heap memory resources to prevent leaks.
** _Source:_ Chronicle Bytes reference counting (reserve/release).
* *CV-NFO-017:* The system *must* provide clear mechanisms for managing buffer lifecycles, especially for off-heap memory.
** _Source:_ Chronicle Bytes API.

== Non-Functional Requirements - Security (NF-S)

* *CV-NFS-018:* The system *must* provide mechanisms for bounds-checked memory access to prevent overflows/underflows during routine operations.
** _Source:_ Chronicle Bytes methods; implicit in Chronicle Values accessors.
* *CV-NFS-019:* When unchecked memory access is permitted for performance reasons (e.g., BytesStore), this *must* be explicitly acknowledged and managed as a controlled risk.
** _Source:_ Chronicle BytesStore design.

== Test / QA Obligations (TEST)

* *CV-TEST-020:* If Chronicle Values is used, dedicated integration and rigorous testing phases *must* be incorporated to validate its suitability.
** _Source:_ Recommendation for Stable status library.
* *CV-TEST-021:* Performance characteristics, including latency and throughput for chosen data manipulation strategies, *must* be benchmarked against project targets.
** _Source:_ General best practice implied by performance focus.

== Documentation Obligations (DOC)

* *CV-DOC-022:* Data schemas defined via Chronicle Values interfaces *must* be documented, including field descriptions, constraints (@MaxUtf8Length, @Array), and any layout annotations (@Group, @Align).
** _Source:_ Derived from Chronicle Values usage.
* *CV-DOC-023:* Guidelines for manual offset management and data interpretation *must* be documented for any components directly using Chronicle Bytes for complex structures.
** _Source:_ Derived from Chronicle Bytes usage.

== Operational / DevOps Concerns (OPS)

* *CV-OPS-024:* The project build system *must* be configured to support Java annotation processing if Chronicle Values is utilized.
** _Source:_ Chronicle Values build process requirement.
* *CV-OPS-025:* Strategies for managing schema evolution and data format compatibility across application versions *must* be defined and documented.
** _Source:_ Implied by analysis of schema evolution for Values and Bytes.

== User Experience (UX - Developer Experience)

* *CV-UX-026:* For well-defined, fixed-layout structured data, the system *should* offer a higher-level, object-oriented abstraction to simplify development and improve type safety.
** _Source:_ Chronicle Values benefits.
* *CV-UX-027:* The learning curve and required expertise for chosen libraries *must* be considered in team structure and training plans.
** _Source:_ Analysis of learning curve.
* *CV-UX-028:* Debugging strategies for both low-level byte manipulation (Chronicle Bytes) and generated code (Chronicle Values) *must* be established.
** _Source:_ Analysis of debugging challenges.

== Compliance / Risk Controls (RISK)

* *CV-RISK-029:* Risks associated with using `sun.misc.Unsafe` (via Chronicle Bytes/Core) *must* be acknowledged, and reliance on library abstractions to mitigate these risks *must* be preferred.
** _Source:_ Unsafe usage in Chronicle Bytes.
* *CV-RISK-030:* Risks associated with the "Stable" status of Chronicle Values (potential bugs, API instability, incomplete features) *must* be actively managed if the library is adopted.
* *CV-RISK-031:* Procedures for diligent pairing of `reserve()` and `release()` calls for off-heap Chronicle Bytes resources *must* be enforced to prevent memory leaks.
** _Source:_ Memory management implications.
